# Teacher Dashboard Specification

## Purpose

Define the later-phase teacher dashboard for classroom use.

## Phase

Teacher dashboard is Phase 2, not MVP, unless explicitly requested earlier.

## Teacher Goals

Teachers need to:

- Manage classes.
- Assign lessons.
- See class mastery.
- Find struggling students.
- Review evidence/discussion/project work.
- Export reports.

## Required Later Sections

1. Class selector
2. Assignment manager
3. Class mastery heatmap
4. Student progress table
5. Weak skill clusters
6. Review compliance
7. Project submissions
8. Discussion moderation queue

## Permissions

Teachers can only access assigned classes and enrolled students.

## Safety Rules

- No direct private messaging with students unless designed with school policy and safeguards.
- Discussion features must be moderated.
- Teacher notes must be private to authorized adults.

## Implementation Notes for Codex

- Do not build this before MVP unless asked.
- Design database so classes/enrollments can be added later without migration chaos.

---

## Definition of Done

This document is usable when:

- The purpose is clear.
- MVP requirements are separated from later-phase requirements.
- Required screens, data, permissions, and edge cases are identified.
- Codex can implement from it without inventing product rules.
- Safety, accessibility, and learning-pillar impacts are considered.

## Data, Permission, and UX Considerations

| Concern | Required Treatment |
|---|---|
| Student data | Collect only what the feature needs; avoid sensitive logs. |
| Role access | Student, parent, teacher, and admin access must be explicit. |
| Accessibility | Use semantic UI, visible focus states, readable language, and non-color-only signals. |
| Empty states | Define what users see when no lessons, reviews, progress, or linked users exist. |
| Error states | Explain what failed and give a safe next action; never expose private internals. |
| Analytics | Track learning events by IDs/tags, not unnecessary personal text. |
